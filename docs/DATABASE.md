# Database Design

The MySQL database contains six related tables. UUID identifiers are generated by TypeORM. All stored timestamps are interpreted as UTC and displayed in Asia/Manila. Password hashes are excluded from API query selections.

## Relationships

- users to patients and doctors: one account has zero or one profile of each type. Each profile belongs to exactly one user.
- patients and doctors to appointments: one-to-many.
- patients and doctors to medical_records: one-to-many.
- appointments to medical_records: optional one-to-one.
- medical_records to prescriptions: one-to-many.

Account details are stored once in users. Role-specific profile data is separate. Appointment resolves the patient/doctor relationship. Prescriptions use separate rows instead of repeated medication columns.

## Deletion and Integrity

Patient and doctor profiles cannot be deleted while referenced by appointments or records. Deleting a medical record cascades to its prescriptions. Deleting an appointment sets its optional medical-record reference to null, although the API only permits deletion of pending appointments. Profile deletion and linked-account deletion are transactional.

## Appointment Constraints

The doctor/start-time index supports availability queries. Active booking interval conflicts are prevented in a transaction using a doctor row lock and an overlap query. State transitions and pending-only edits/deletions are service rules. The schema is created explicitly by setup; startup synchronization is disabled.
