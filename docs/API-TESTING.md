# API Testing

Base URL: `http://localhost:4000/api/v1`. Start the application with `npm run dev:offline`, or start only the API with `npm run api:offline`. The managed MySQL instance starts automatically.

## Postman

1. Import `postman/MediConnect.postman_collection.json`.
2. Import the private `.local/postman/MediConnect.local.postman_environment.json` generated by `npm run setup:testing`, then select **MediConnect Local Offline**. It supplies the existing credentials from your local `.env`; keep this file local. Alternatively set patientEmail/patientPassword, doctorEmail/doctorPassword and adminEmail/adminPassword in collection Variables. Use an existing patient and an active doctor.
3. Run Authentication first. Scripts save separate role tokens.
4. Run Patients CRUD and Doctors CRUD to verify full resource lifecycles using newly created synthetic records.
5. Run Appointments to demonstrate POST, GET, PUT, PATCH and DELETE. PUT requires startsAt, reason and notes; notes may be null. PATCH preserves omitted values. DELETE returns 204 with an empty body; a follow-up GET returns 404.
6. Run Consultation Records, User Administration and Validation/Access Control.

Requests include assertions for expected status codes and exclusion of password hashes. Invalid credentials/missing tokens must return 401; role violations return 403; invalid DTOs return 422; malformed JSON returns 400; conflicts return 409. These are intended error responses, not server failures.

The appointment must remain PENDING during the five-method demo. Approval and medical-record creation are a separate workflow. A completed consultation appointment remains in history when testing manually; the automated runner removes only its own synthetic verification records afterwards.

## Automated run

Run `npm run setup:testing` once while internet is available. This installs pinned Newman 6.2.3 under ignored `.local/api-testing`, outside the application dependency tree.

Then run `npm run test:offline` while the API is running. It launches the locally installed runner and restricts Node outbound connections to loopback; it never uses npm exec, npx or registry downloads. `npm run test:api` also uses the installed runner, without the explicit network guard. Credentials come from ignored `.env`, and a sanitized summary is written to `docs/VERIFICATION.json`. Only known records created by that run are removed. Existing appointments and medical records are preserved.

If the runner is missing, the command stops with setup instructions instead of attempting an internet download.

## Code walkthrough

For a booking, open `backend/src/appointments/appointments.ts`. The controller receives JSON, the Zod pipe validates it, the service checks the patient and doctor availability, and the TypeORM repository/transaction writes MySQL. Follow the saved appointment back to the response. Entity relationships are in `backend/src/database/entities.ts`.

## Database check

Connect a MySQL client using the local connection settings. Inspect the appointments table before and after PUT/PATCH, matching the ID returned by POST. After DELETE, the same ID should no longer exist. Do not expose the populated .env or password hashes in screenshots or recordings.

## Five-method demonstration without internet

Use Postman Desktop and a local workspace/agent, with the collection already imported. Set `baseUrl` to `http://localhost:4000/api/v1`. No internet or Apache service is needed; the local MySQL and Node API must be running.

1. In **01 Authentication**, send **Health**, **Login patient**, **Login doctor** and **Login admin**. The login scripts save each JWT. Send **List doctors** in **03 Doctors CRUD** to set the active doctor ID.
2. In **04 Appointments**, send **Create appointment** (POST): expect 201 and save the appointment ID.
3. Send **Get appointment** (GET): expect 200 for that ID.
4. Send **Replace appointment** (PUT): expect 200. Send all editable fields: startsAt, reason and notes.
5. Send **Patch appointment** (PATCH): expect 200. Only the selected field changes.
6. Send **Delete pending appointment** (DELETE): expect 204 with an empty body.
7. Send **Verify appointment deleted** (GET): expect 404. This confirms deletion and is an intentional response.

Keep this booking PENDING throughout the sequence. Run the separate consultation workflow after the five-method demonstration. Re-login if the one-hour JWT expires. POST/PUT dates must remain in the future; the collection generates fresh test times.

Run the local sequence once after switching Wi-Fi off on the same computer before the presentation. The automated offline check blocks non-local connections for the application and test processes without changing the computer's network adapters.

## Postman offline interface

The installed desktop application exposes **Local mode** in its bottom-left corner. A direct `GET http://localhost:4000/api/v1/health` was also checked in this interface and returned 200 with the local MySQL health response.

Postman versions differ: the [lightweight offline client](https://learning.postman.com/docs/getting-started/basics/using-api-client) supports individual requests, but may not provide collections, environments or variables. In that mode, enter the full localhost URL, use Body > raw > JSON for login, copy `data.accessToken` from the successful response and paste it under Authorization > Bearer Token for protected requests. Use the appointment ID returned by POST in each following GET/PUT/PATCH/DELETE URL. Login and all API/database operations remain local.

The collection JSON uses the implemented MySQL API: generated UUID resource IDs, account credentials when creating patient/doctor accounts, and 422 for DTO validation. Older laboratory design examples using CUIDs or external authentication are not live-test payloads for this backend.
